# Local requirement map

The public authenticated action service and real Postgres provide the primary behavioral evidence. Mounted clients provide the rendered layer. These results do not establish native, browser, hosted or release acceptance.

| Requirement | Binding evidence | Result and limit |
| --- | --- | --- |
| Saved and failed independent additions | Mobile partial case; Web `names saved, failed` case | A real trigger fails the phone addition. Another addition is saved. The receipt distribution is `reused, reused, failed, created`. Each saved task has its own row. The failed addition is named. |
| Not-attempted work | Same partial cases, with an excluded library addition | The applied server proposal records the user exclusion. Both panels display `Left out after your review`. No library task exists. This is a user exclusion, not a server failure or dependent-operation failure. |
| Conflict | Web partial case and offline case; retained Mobile offline case | The exact historical Undo names the changed task or operation. The newer revision and Waiting reason survive. Existing per-operation conflict panels remain in use. |
| Retry only failed work | Mobile and Web partial cases | Retry contains one original failed item ID. The successful row is byte-identical across retry. No excluded task is created. |
| Restart while lookup is still failed | `restart-create-final` plus `restart-resume-final`; corresponding Web pair | Two separate test processes share only storage-boundary bytes and a synthetic Auth fixture. The first exits before any receipt exists. The second exposes lookup, blocks approval, and uses the original ID for both failed and successful lookups. Only confirmed not-applied plus an explicit retry can write. |
| Pending lookup | Real Postgres lock cases on both clients | Public status returns pending while the operation lock is held. Approval presses send no second write. After release, not-applied permits an explicit retry with the same ID. |
| Committed response loss | Retained Mobile and Web lost-after-commit cases, run with the local stack | A real successful response is discarded only after commit. Lookup failure stays unresolved. One receipt and task remain. Server proposal/receipt recovery is reused. |
| Approved review and changed context | Retained Web draft, exclusion, profile-change and two-review cases; Mobile retained cases | Drafts write nothing. Relevant changes require a new approval. Both unfinished revised reviews remain reachable after remount. No batch endpoint was added. |
| Plan, task, step, reminder and context | Mobile core case; Web core case | Mobile covers approved personal/profile context. Web adds a checked step, Waiting reason and reviewed Vancouver reminder. IDs remain stable after reopening. A checked step does not complete its parent. |
| Offline and reconnect | Both offline cases | Cached progress is labelled stale. Offline controls cannot write. Reconnect reads a real other-device edit. Reviewed removal disables stale controls. |
| Account ownership and cleanup | Mobile ownership case; Web offline/account case; UserProvider cases | Same-account token refresh keeps recovery. Account replacement and confirmed sign-out remove it. A late response cannot restore it. Failed Auth reads do not count as sign-out. Rapid account replacement clears the old record even when the final account is the original one. |
| Drafts and focus | Mobile core/partial cases; Web core/partial/offline cases; retained Web review cases | Message drafts survive panel updates and close. The Waiting field retains node identity. Web input focus remains in the drawer. This does not prove native focus or draft persistence across a full process restart. |
| Translations and accessibility | Seven locale edits; parity checks; rendered controls and focus; four retained disclosure checks | The failure sentence names only failed work. Existing translated exclusion copy is reused. Mobile retains its polite live region. Web exclusion lines use `role=status`. Existing Reveal and reduced-motion rules remain. No new control or animation was added. |

The four outcomes are identified through existing plan results, the applied proposal and exact per-operation conflict receipts. There is no invented four-item batch response. The generic action endpoint still accepts one operation. The restart record contains references only. It contains no task text, raw operations, message draft or executable approval payload. Restored state permits lookup first. An apply retry re-reads the proposal and verifies its revision before the explicit retry uses its original ID.
