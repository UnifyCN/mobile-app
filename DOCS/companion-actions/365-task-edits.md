# #365 Edit existing tasks through clear or proposed chat actions: mobile and web

Spec: UnifyCN/mobile-app#359. Ticket: #365. Builds on #360 (contract), #361 (task actions), #362 (context reads) and #363 (task creation). Date: 2026-10-27/28. Accepted #366 (task steps) was integrated during this work. The #365 migration builds on the #366 shared action functions below. The original #365 candidate excluded #364. The composition candidate includes accepted #364 and reviewed #370. See `evidence/365-370-composition-r1/README.md` for the composition checks and proof limits.

A user changes an existing Checklist task's title, description, priority, state or waiting reason from Companion. A clear direct command in the user's own message ("Rename task "Get a phone plan" to "Get a prepaid plan"") makes exactly that one change with no model request; an unclear one asks a question and writes nothing. A change the answer suggests is a server-owned draft: the card says "Draft · not saved yet", and review (direction B: mobile bottom sheet, web overlay drawer) shows each field's current value and the value approval saves. Approval binds to the draft revision and to the values of the fields it changes. Every saved change has a receipt that names the field, the value before and the value after, with revision-checked Undo of that receipt only. No removal, steps, plans, reminders, job UI, external submission, messaging, booking or upload.

## Decision: where a per-user edit is stored

Read from the consumers (mobile `services/checklist/getChecklistWithUserProgress.ts`, `customChecklistTasks.ts`; web `services/checklist.ts`; rag-query `lib/context/appContext.ts`; released v1.6.0 per #360):

- A **custom task**'s title, description and priority are its own `custom_checklist_tasks` columns. Every Checklist (mobile, web, released v1.6.0) reads them with `select('*')`. An edit writes those columns, so it shows everywhere, in Checklist, in new conversations and on older clients, with no new column, no schema change and no client change for the read path.
- A **published (Sanity) task**'s title, description and priority are shared, localized content. Changing them for one account would need an override column no Checklist reads (older clients would keep showing the content text, so two versions of one task would disagree). They are therefore **not editable** here: the operation, the command and the model suggestion refuse them (`shared_task_field`, "This is a suggested Unify task, so its title, description and priority are the same for everyone…"). Its state and waiting reason are the per-user #361 columns of `user_tasks`, as before.
- State and waiting reason keep the #361 operation `task.set_state` and its executor; no new state path.

This is the narrowest representation that keeps the hosted-shape baseline and older-client behaviour: the migration adds no table and no column (one widened check constraint for the new proposal kind).

Anything else is not a command (an ordinary question goes to the model). This is not a natural-language parser: no other phrasing, no guessing of language or task.

One change per line, with only its own quote marks (S365-001, corrections r1): a title, a new title, a description or a waiting reason cannot contain a quote mark. A line with more quote marks than its one change uses (a second command run on, `Rename task "Phone" to "Mobile" and rename task "Bank" to "Credit union"`, or a quote inside a title) is `multiple_changes`: a question, no write, and a forged operation under it is refused at apply, because apply resolves the message again with the same rule.

### Behaviour rules (tested)

- **Target and fields from live account data.** The command's task must be exactly one live task of the account (custom or published, as the Checklist shows it; another account's, another province's or a removed task never matches). Zero matches → `task_not_found`; two or more → `task_ambiguous` (titles shown, none changed); published title/description/priority → `shared_task_field`; unknown label → `invalid_value`; same value → `no_change`; published content unreadable → `tasks_unavailable`; several lines with an edit → `multiple_changes`. Each is a localized question saved as an assistant message; nothing is written and a forged operation under such a message is refused.
- **A command authorizes only its exact change, once.** The service reads the user's own saved message itself, resolves it again at apply and compares the submitted operation (any other title, task, field or state is 403). One message, one write (`command_already_used`); a retry of the same committed operation replays its receipt even after the rename changed what the message resolves to. A change between reading and applying is a `revision_conflict`; nothing is written and the message can be used once it is re-read. "Mark … as waiting" without a reason keeps a waiting task's saved reason.
- **Suggested edits need approval.** Preparing writes only the proposal, at the task's current revision, with the values it changes from. Approval with a different proposal revision or operation is refused; two approvals of one draft apply once (held-lock race tested). Before the write the server re-reads the fields the change touches: a newer value of such a field (from any client, including an older one writing the table directly) returns `needs_review` with a revised draft (old and current value, `review_reason: context_changed`) and writes nothing; the old approval no longer applies. A change to another field of the same task (for example its state) is not relevant: the approved change applies at the current revision without a new approval and keeps that state.
- **Completion stays explicit.** Completed is only a command naming it or an approved draft naming it; the review says "Select Completed when the whole task is done. Your steps do not complete it." Nothing else in this slice marks a task complete or claims steps were done.
- **Receipts are history.** An edit receipt records the title after the change and each changed field with before/after values; a later edit does not rewrite it and it shows "This task changed after this" once the task moves on. A state change receipt also records the waiting reason before and after (`before_waiting_reason`, `after_waiting_reason`; S365-002, corrections r1); a changed reason shows as a `Waiting for: “Friday” → “Monday”` line, so a reason-only change does not read Waiting → Waiting. Lookup, replay, the conversation read and Undo return the recorded reasons. A receipt saved before this has neither field and shows no reason line. Reason text is not sent to analytics.
- **Undo** restores exactly the recorded earlier values while the task is at the receipt's revision; after a newer edit nothing changes, the newer values are kept and a compensating change at the current revision is offered ("Restore earlier values", approved_proposal). Competing Undos apply once. State-command Undo restores the earlier state and reason (inherited #361 path).
- **Unchanged rules from #361/#363:** account from the JWT only; operation identity per intent; unknown outcome is looked up before retry; `pending`/lookup failure never write; writes need a fresh successful read; the AI limit does not block any action; drafts and caches are per account; composer drafts survive the sheet/drawer.

## How to run

Backend (web repo; own disposable stack: change `supabase/tests/companion-actions/supabase/config.toml` project id/ports, or use the committed `unify-actions-363` values; `ACTIONS_CONTENT_PORT` names the #366 published-content stand-in port): `supabase/tests/companion-actions/run.sh` (all files) or `run.sh edit_test.ts`. With `ACTIONS_MOBILE_LOCALES=<mobile>/unify-front-end/i18n/locales` the priority-label test also reads the mobile labels. Mutations: `python3 -I supabase/tests/companion-actions/mutation_check.py`.
Edge workflow (web): both steps of `.github/workflows/edge-functions.yml`.
Mobile: `npx jest __tests__/companionActions/taskEdit.test.tsx --watchAll=false`; real stack: `ACTIONS_API_URL=… ACTIONS_ANON_KEY=… ACTIONS_SERVICE_ROLE_KEY=… ACTIONS_DB_CONTAINER=supabase_db_<project> ACTIONS_REST_CONTAINER=supabase_rest_<project> npx jest __tests__/companionActions/companionActionsLocalStack.test.tsx --watchAll=false`; gates `npm run test:ci`, `typecheck`, `lint`, `check-i18n`, `npx expo export --platform ios --platform android`.
Web: `npx vitest run components/companion/tasks/TaskEdit.test.tsx`; gates `npm test`, `npx tsc --noEmit`, `npm run check-i18n`, `npx eslint .`, `npm run build`.
